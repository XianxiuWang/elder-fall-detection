四、踩过的坑 — 绝对不要再踩 🚫 (新增 + 之前的所有)

  === 本次新踩的坑 (7/25) ===

  18. npz 文件的 keypoints 字段名不统一!
      → LE2I .npz 用 'keypoints' 键
      → URFD .npz 用 'landmarks' 键
      → 代码里必须双键兼容:
          kp = data.get('keypoints')
          if kp is None: kp = data.get('landmarks')

  19. npz 文件的标签字段名也不统一!
      → LE2I: 'labels' (N维数组, 逐帧标注, -1=未标注)
      → URFD: 'label' (0维标量 0/1) 或 'action' (字符串如 "unknown")
      → 标签读取必须多键尝试 + 类型检测:
          lbl = d.get('category')
          if lbl is None: lbl = d.get('label')
          if lbl is None: lbl = d.get('action')
          if isinstance(lbl, (str, bytes)):
              lbl = 1 if 'fall' in str(lbl).lower() else 0
          if hasattr(lbl, 'ndim') and lbl.ndim == 0:
              lbl = int(lbl)
          if lbl is None: lbl = 0

  20. numpy 数组做布尔判断的经典 Python 陷阱!
      这种代码会炸:
        data.get('keypoints') or data.get('landmarks')
      → 报错: "The truth value of an array with more than one element is ambiguous"
      → 必须写成:
        kp = data.get('keypoints')
        if kp is None: kp = data.get('landmarks')

  21. Python 零值真值判断的经典陷阱!
      这种代码对标签值 0 会出错:
        lbl = d.get('category') or d.get('label') or d.get('action')
      → 当 label==0 (正常视频) 时, int(0) 是 falsy
      → Python 会跳过 label 去取 action, action 可能是 None 或字符串
      → 导致 int(None) 崩溃 或 int("unknown") 崩溃
      → 解决方案: 逐个用 is None 检查, 别用 or 链

  22. LightGBM 在 conda 环境下"卡住"问题
      → 症状: 训练 silence 模式下, 长时间无输出, 像冻住了
      → 实际原因: log_evaluation(0) callback + verbose=-1 的组合导致
        stdout 不冲洗, 看起来像挂了但其实在正常跑
      → 解决方案:
        - 用 verbose=-1 (不是 0) 关闭自动打印
        - callbacks=[lgb.early_stopping(30), lgb.log_evaluation(0)]
        - Python 启动时加 -u 标志禁用缓冲
        - 或者写训练日志到文件, 不看终端输出
      → 训练 4,881 样本 × 200 轮 只需 ~5 秒, 不要以为卡了

  23. 序列评估在大数据集上"卡住"问题
      → 症状: 130 个视频的序列评估, 5分钟没输出, 像死循环
      → 实际原因: 每个视频要重新加载 .npz + 逐窗口提取特征 + 
        模型推理, stdout 缓冲导致看不出进度
      → 解决方案 (最终使用的): 
        - 文件日志 + flush=True (不依赖终端, 用 type 命令读取)
        - 每 30 个视频输出一次进度
        - LE2I 130 视频 ≈ 28 秒, URFD 70 视频 ≈ 17 秒
      → 总计 45 秒, 不要急着 kill!

  34. ★ Python 文件日志在多进程/多脚本间会锁死!
      → 上一个 Python 进程崩溃后没有关闭 FileHandler → 文件被 Windows 锁定
      → 新进程无法打开同名日志文件 → logging.getLogger() 静默失败 → 脚本像卡死一样
      → 症状: 进程 alive 但 stdout 和日志文件都无输出
      → 解决方法:
        - 每次运行使用不同的日志文件名 (加时间戳)
        - 或者完全不写文件日志，只用 stdout + sys.stdout.flush()
        - 被锁时用 lsof / Unlocker 强制释放句柄
      → 本日因此浪费了 30+ 分钟反复 kill 重启

  35. ★ 长合集视频 (50 Ways to... 系列) 在 MediaPipe 上极慢
      → "100种走的动物.mp4"(32MB, ~1500帧@fps=5) MediaPipe 处理需 8-10 分钟
      → 帧数多不是问题，是 MediaPipe static_image_mode 逐帧推理本身就慢
      → 解决方案: 按文件大小跳过 >20MB 的视频，用单独的 fps=3 参数处理
      → 或者分两个阶段: ffmpeg 批量解所有帧到磁盘 → 再用 MediaPipe 单独跑

  36. ★ 子会话 (sessions_spawn) 超时问题
      → runTimeoutSeconds=3600 不代表子会话能跑 1 小时
      → 实际超时取决于子会话内每个 tool call 的 timeout
      → exec 的 timeout=1800 但中途 process.poll 不续期
      → 建议: 长时间任务直接用主会话 exec(background=true)，不用 sessions_spawn
      → 或给子会话的每次 exec timeout=600 并频繁 poll 续期

  37. f-string 里不能有反斜杠!
      → 错误: print(f"  {os.path.join(d,f)}: ...")
      → 正确: p = os.path.join(d, f); print(f"  {p}: ...")
      → 这个 Python 语法限制在写 ad-hoc 检查脚本时频繁触发

  38. piped stdout 在 Windows cmd 下不可靠
      → process.log 读到的输出可能是缓冲前的 (几分钟前的内容)
      → 真实进度比可见输出快很多——不要因为看到旧日志就 kill
      → 用检查文件/文件夹计数来验证实际进度（比看日志可靠）
      → 例如: 数 npz 文件数、看 tmp 目录变化

  39. os.listdir 中文文件名显示乱码但操作正常
      → Windows cmd 的 GBK 编码与 Python 的 UTF-8 不兼容导致显示乱码
      → 但 os.path.exists()、open()、字符串匹配都能正常工作
      → 分类逻辑 ('摔' in filename) 用的是 Python str, 不受显示乱码影响

  40. skip-already-extracted 的断点续传很重要
      → 提取 135 个视频中断时, 重新跑脚本会浪费已提取的文件
      → 在脚本开头检查 output_path 是否已存在 + 是否 valid (≥10帧)
