## 已完成的工作

### Bug #1：label_dur 死锁（✅ 已修复并验证）

**问题**：摔倒视频开头 2.9s 被判为 Walking 后，后续所有帧都被锁在 Walking（即使 90% 帧是 Fall）。

**根因**：
```python
# 旧代码（v2）
if self.label_dur < self.min_dur:
    self.label_dur += 1          # ← 递增计数器
    final = self.cur_label       # ← 强制保持旧标签
```
每帧 `label_dur++`，但切换条件也是 `label_dur >= min_dur`，导致"越想切换越等越长"的死锁。

**修复方案**：引入独立的 `switch_pending` 计数器：
- 想切换时 → `switch_pending++`（不碰 label_dur）
- `switch_pending >= MIN_DURATION` → 切换批准，重置所有状态
- 不想切换时 → `switch_pending = 0`

### Bug #2：Fall hold 绕过投票机制（✅ 已修复并验证）

**问题**：修复 Bug#1 后，Walk 视频出现 34-36 个虚假 Fall 检测（v2 被 Bug#1 掩盖了，显示为 0）。

**根因**：Fall hold 太激进——一旦 `fall_ctr > 0`（之前检测到过 Fall），后续帧只要 `fall_p >= 0.35` 就直接强改 Fall，**完全忽略 7 帧多数投票结果**。Walk 视频中一个真误报激活 hold 后，连锁触发后续假 Fall。

**修复尝试历程**（记录了每次尝试和结果）：
| 尝试 | 方案 | Walk Fall 数 | 结论 |
|:---|:---|:---:|:---|
| 1 | Fall-priority 平局（fall_p > 0.5） | 36 | ❌ 不够 |
| 2 | 提高到 fall_p > 0.8 | 35 | ❌ 不够 |
| 3 | 移除 Fall-priority，仅靠 switch_pending | 34 | ❌ 不够 |
| 4 | **Fall hold 加投票校验 `fall_in_vote >= 2`** | **29** | ✅ 最优 |

**最终修复代码**：
```python
fall_in_vote = cnt.get(FALL_ID, 0)
if self.fall_ctr > 0 and self.fall_ctr <= self.fall_hold \
   and fall_p >= self.fall_thresh and fall_in_vote >= 2:
    final = FALL_ID
```
关键：即使 hold 激活，也必须至少有 2 票在 7 帧窗口内投了 Fall。

## 当前卡点：Walk 视频 29 个残余误报 —— 模型天花板

### 根因分析

这个问题不（全）是时序过滤器的锅。看数据链路：

```
原始模型输出（Walk 视频，496 窗口）：
  Fall 预测: 59 窗口 (11.9%)  ← 模型本身就在奇怪走路姿势上高置信度判 Fall
  
时序过滤器 v3 处理后：
  Fall 输出: 29 窗口 (5.8%)   ← 已经压了一半，剩下的是"连续、高置信度"误报
```

**为什么时序过滤器无法完全消除**：
- 这 29 个 Fall 是连续的（3 个事件各 ~6-7s）
- 它们的 fall_p 都在 0.5+，投票窗口内 Fall >= 3/7
- 时序过滤器只能处理"孤立"误报（前后帧不一致），处理不了"模型固执地认为这就是 Fall"的情况

**为什么模型会这样**：
- 100 种走路方式包含大量**奇怪姿势**：蛇形走、深蹲走、蹒跚走、侧身匍匐、手撑地爬行……
- 这些姿势在关键点空间上确实更接近"摔倒"而非"正常行走"
- V5 训练数据中 Walking 类可能缺少这些极端姿势

### 结论

| 指标 | 值 | 说明 |
|:---|:---|:---|
| 时序过滤器 v3 正确性 | ✅ 已验证 | 两个 bug 修复后行为合理 |
| v2 的 0 Fall | ❌ Bug 假象 | label_dur 死锁掩盖了真实误报 |
| Walk 5.8% FPR | ⚠️ 模型级天花板 | 除非增加 Walking 训练数据，否则无法进一步降低 |

## ⚠️ 绝对不要再踩的坑

1. **`label_dur` 死锁**：递增同一个变量既是"等"又是"判"，必然越等越长。**用独立的 `switch_pending` 计数器**，不要复用 label_dur。

2. **Fall hold 必须经过投票**：`fall_ctr > 0` 不能单方面推翻 `cnt.most_common()` 的结果。最低要求：**当前窗口内至少有 2 票投了 Fall**。

3. **v3 诚实 > v2 虚假干净**：0 Fall 不一定是好结果——它可能是另一个 bug 在掩盖问题。有了 bug 先问"这是不是我看到的真结果"而不是追求数字好看。

4. **2D 倾斜度特征不可靠**（来自 08-05 交接）：正面和背面视角下 tilt 趋近于零。不要在这上面浪费时间。

5. **新数据引入后 Walking/Standing 精度下降**：StandUp+WakeUp 数据的姿势多样性增加了分类难度。任何新数据加入后必须在 Walk 视频上做回归测试。

6. **混淆矩阵不等同于视频推理结果**：静态混淆矩阵上的误报（如 Standing→Fall 5 个）不一定等于视频推理中的误报——关键帧可能被周围的正确预测纠正。

## ⚠️ 今天新踩的坑

1. **`cap.set(CAP_PROP_POS_FRAMES)` 对 H.264 MP4 极慢**：每次 seek 需要从最近 keyframe 解码到目标帧，跳跃 500+ 帧的 seek 可耗时 10-20 秒。**方案**：按簇跳帧 + 簇内顺序读，减少 seek 次数，每次 seek 后 buffer 15 帧避免解码不准。

2. **深度图 PNG 对 MediaPipe Pose 无效**：`F:\动作数据集\数据集（1）\Subject.X\Walk\` 的 PNG 图片是深度相机输出的伪彩色图，MediaPipe Pose 无法从中检测人体关键点。**不要在这个数据源上浪费时间。**

3. **训练脚本与推理脚本的特征提取器必须严格一致**：V6 训练用了 59 维特征（+8 tilt），推理时必须同步升级 `video_inference.py` 中的 `EnhancedFeatureExtractor`，否则模型加载会报维度不匹配或推理结果完全错误。

4. **Windows 中文路径 + conda run 的 GBK 编码问题**：`conda run -n fall python xx.py` 的 stdout 默认用 GBK 编码，会导致 Unicode 特殊字符（如 ⚠️）报错。**方案**：不用 `conda run`，直接用 `d:\Anaconda3\envs\fall\python.exe -u`，并在脚本开头加 `sys.stdout.reconfigure(encoding='utf-8')`。

5. **推理结果 JSON 文件命名**：如果视频文件名含中文，JSON 文件名也会含中文（如 `results_100 Ways to Walk100种走路方式.json`）。读取时注意 encoding='utf-8'。
