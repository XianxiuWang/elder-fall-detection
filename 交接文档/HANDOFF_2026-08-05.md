## 今日新增：时序过滤器回归测试 (video_inference.py)

### 背景

`video_inference.py` 实现了完整的视频流推理管线：
```
RGB 视频 → MediaPipe Pose → 30帧滑窗 → V5 分类器 → 时序过滤器 → JSON
```

**TemporalFilter** 类内置在 video_inference.py 中（第 72-143 行），参数：
- VOTE_WINDOW = 7（多数投票窗口）
- FALL_HOLD = 15（检测到 Fall 后保持帧数）
- MIN_DURATION = 9（标签切换最少连续帧数）
- FALL_PROB_THRESH = 0.35

### 发现的 Bug #1：label_dur 死锁（✅ 已修复）

**症状**：摔倒视频开头 2.9s 被判为 Walking 后，后续所有帧都被锁在 Walking（即使 90% 是 Fall）。

**根因**：
```python
# 旧代码（v2）
if self.label_dur < self.min_dur:
    self.label_dur += 1
    final = self.cur_label  # ← 增加 label_dur 的同时不切换
```
每帧 label_dur++，但切换条件也是 `label_dur >= min_dur`，形成"越等越等"的陷阱——因为 `label_dur` 从不等号两边都被递增。

**修复**：引入 `switch_pending` 计数器：
```python
# 新代码（v3）
if final != self.cur_label and self.cur_label >= 0:
    self.switch_pending += 1              # 累计"想切换"的帧数
    if self.switch_pending < self.min_dur:
        final = self.cur_label            # 还没到阈值，保持
    else:
        self.switch_pending = 0           # 切换批准
        self.label_dur = 0
        self.cur_label = final
else:
    self.switch_pending = 0
```

### 发现的 Bug #2：Fall hold 绕过投票（✅ 已修复）

**症状**：修复 Bug#1 后，Walk 视频出现 34-36 个虚假 Fall 检测（v2 是 0 个）。

**根因**：Fall hold 机制太激进：
```python
# 问题代码
if self.fall_ctr > 0 and self.fall_ctr <= self.fall_hold and fall_p >= self.fall_thresh:
    final = FALL_ID  # ← 跳过投票，直接强制 Fall
```
Walk 视频中一个高置信度误报 Fall（如步行中突然下蹲/踉跄），激活 `fall_ctr > 0`，然后后续帧只要 `fall_p >= 0.35` 就被强改 Fall，**完全忽略投票结果**。

**修复尝试历程**：
1. ✅ 添加 Fall-priority 平局逻辑（fall_p > 0.5 时优先 Fall）→ Walk 仍有 36 Fall ❌
2. ❌ 提高到 fall_p > 0.8 → Walk 仍有 35 Fall ❌
3. ❌ 移除 Fall-priority 平局（仅靠 switch_pending）→ Walk 仍有 34 Fall ❌
4. ✅ **Fall hold 加投票校验**：`fall_in_vote >= 2` 才允许 hold 生效 → Walk 降到 **29 Fall** ✅

关键代码修改（video_inference.py 第 ~108 行）：
```python
# 修复后
fall_in_vote = cnt.get(FALL_ID, 0)
if self.fall_ctr > 0 and self.fall_ctr <= self.fall_hold and fall_p >= self.fall_thresh and fall_in_vote >= 2:
    final = FALL_ID
```

**残余误报分析**：Walk 视频残余 29 个 Fall（5.8%），根因是**模型级别问题**——原始模型在 Walk 视频有 59 个高置信度误报（12%）。这些误报集中出现在"奇怪走路姿势"（蛇形走、蹒跚走、深蹲走），模型本身判断它们是 Fall。时序过滤器无法完全消除这些误报，因为它们是**连续的、高置信度**的。v2 的 0 Fall 是 `label_dur` 死锁 bug 的虚假结果。

**结论**：29/496 (5.8%) 假阳率在"100种走路方式"视频上是合理下限。要进一步降低，需要**增加 Walking 训练数据**（尤其是特殊走路姿势）来提升模型区分能力。

## ⚠️ 绝对不要再踩的坑

1. **`label_dur` 死锁**：递增同一个变量既是"等"又是"判"，必然越等越长。**用独立的 `switch_pending` 计数器**。

2. **Fall hold 别跳过投票**：`fall_ctr > 0` 不应该单方面推翻 `cnt.most_common()` 的结果。至少要检查当前窗口是不是真的有 Fall。

3. **2D 倾斜度特征不可靠**：正面和背面视角下 tilt 趋近于零。不要在这上面浪费时间。

4. **混淆矩阵必须在时序上下文中验证**：静态混淆矩阵上的误报（如 Standing→Fall 5 个）不一定等于视频推理中的误报——关键帧可能被周围的正确预测纠正。

5. **新数据引入后 Walking/Standing 精度下降**：StandUp+WakeUp 数据的姿势多样性增加了分类难度。如果后续要用这批模型做视频推理，优先在 Walk 视频上做回归测试。
