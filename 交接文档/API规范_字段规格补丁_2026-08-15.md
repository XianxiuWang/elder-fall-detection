## 一、字段单位/量纲补全（当前文档缺失，各模块已出现量纲不一致）

### 1. 步态上传接口 `POST /api/v1/gait-data/`（4.3.2）

| 字段 | 单位/量纲 | 正常值参考 | 说明 |
|------|-----------|-----------|------|
| `elderly_id` | int | 1 | 老人编号 |
| `walking_speed` | **m/s** | 0.8 ~ 1.4 | 边缘端已按 m/s 输出（cm/s ÷100） |
| `step_length` | **m** | 0.45 ~ 0.75 | 边缘端已按米输出（归一化×1.8 标定） |
| `body_sway` | 归一化坐标 ×100 | 2 ~ 10 | 无量纲晃动幅度，越大越不稳 |
| `balance_score` | 0 ~ 100 | 50 ~ 95 | 平衡评分，越高越好 |

⚠️ **历史坑**：walking_speed 此前按 cm/s 输出（约 80~120），与规范示例 1.2（m/s）差 100 倍。现已统一为 **m/s**。

### 2. 姿态分析返回 `POST /api/v1/pose-analysis/simulate`（4.3.1）

| 字段 | 单位/量纲 |
|------|-----------|
| `walking_speed` | m/s |
| `step_length` | m |
| `body_sway` | 归一化坐标 ×100 |
| `balance_score` | 0 ~ 100 |
| `gait_score` | 0 ~ 100 |

⚠️ `balance_score` 与 `gait_score` 语义区分需明确：建议 `balance_score`=平衡能力（侧重晃动/稳定性），`gait_score`=步态综合（侧重速度/步长规律性）。4.3.2 上传仅需 `balance_score`，与 4.3.1 返回字段的一致性请后端确认。

## 二、路由尾斜杠统一（当前文档内部不统一，FastAPI 会 307/404）

文档现状：

- 带尾斜杠：`/elderly/`、`/health-record/`、`/gait-data/`、`/face-analysis/`、`/alarm-record/`
- 不带尾斜杠：`/pose-analysis/simulate`、`/fall-prediction/run`、`/scam-detection/analyze`、`/conversation/chat`、`/ai-analysis/dashboard-summary`

**建议**：全部统一为**带尾斜杠**（FastAPI 最省心，且集合型资源语义更贴切），后端路由定义、客户端请求、文档三方保持一致。若统一动作成本高，至少做到**每个接口三方一致**。

## 三、其他工程细节建议

1. **失败响应补 `data` 字段**：建议失败返回也带 `"data": null`，与成功结构对齐，前端无需分支判断。
   ```json
   { "code": 400, "message": "参数错误", "data": null }
   ```
2. **时间格式统一 ISO 8601**：`create_time` 建议用 `"2026-07-18T16:30:00+08:00"`（InfluxDB 入库需 RFC3339，空格分隔无时区需额外转换）。
3. **文档硬件型号笔误**：8.1 节"Orange Pi 5 Plus (RK3588)"应为"Orange Pi 5 Pro (RK3588S)"。
