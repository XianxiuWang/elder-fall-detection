           的检测率本就偏低
        b) 视频分辨率 544×960, 人像在画面中占比可能较小
        c) model_complexity=1 可能不够 (虽然设 2 会慢很多)
    → 影响评估:
        - 对摔倒视频影响有限 (摔倒瞬间仍能检测到, risk 还是上去了)
        - 但对日常监护场景 (正常行走、坐着) 可能漏掉大量帧
        - 这可能是产品级部署的致命问题
    → 需要验证: 用正常行走视频 / 摄像头实时测试,
      看正常姿态下 MediaPipe 检测率能到多少

  [P1] 处理速度 5.9 fps — 远低于实时要求
    → 视频是 30fps, 但管线只能跑 5.9fps (5x 慢放)
    → 瓶颈分析: MediaPipe Pose (model_complexity=1) 是主要耗时

四、踩过的坑 — 绝对不要再踩 🚫 (今日新增)

  48. Windows 终端 (GBK) 打印 emoji 必定崩溃 ★ 新坑
      → 症状: UnicodeEncodeError: 'gbk' codec can't encode character '\U0001f4ca'
      → 原因: Windows 默认控制台编码是 GBK, emoji 是多字节 Unicode
      → 解决: 所有含 emoji/diacritics 的输出写到文件 (encoding='utf-8'),
        终端 print 只用 ASCII 安全字符
      → 永远不要在 Windows 终端 print emoji! 用 [PASS]/[FAIL]/[WARN] 代替 ✅/❌/⚠️

  49. 长视频测试需要足够超时时间
      → 本视频 2869 帧 @ 5.9fps = ~485s (~8 分钟)
      → 上次只给了 420s 超时, 在 88% 时被 kill 了
      → 教训: 计算完所有帧的预估时间后, timeout 至少 +20% 余量

  50. 视频测试脚本用文件输出比终端输出稳定 100 倍
      → 终端输出有缓冲、编码、行长度截断等问题
      → 文件输出天然支持 UTF-8、不受终端限制、可以事后查看
      → 后续所有批量测试脚本默认走文件输出
