  46. cv2.imwrite 中文路径下可能静默失败 (不报错, 文件不产生)
      → Windows 上 OpenCV 内部用窄字符 API, 如果路径含中文
        (如 "E:\老人跌倒\alerts\") cv2.imwrite 可能静默失败
      → 兜底方案: cv2.imencode → numpy tobytes → Python open() 二进制写入

      → 永远不要假设 cv2.imwrite 在中文路径下能正常工作

  47. pypdf extract_text 中文提取后是乱码 → 不需要 pypdf
      → pypdf 专为英文 PDF 设计, 对中文学术论文几乎没用
      → 如果论文 PDF 是扫描版, 唯一的办法是多模态 API (Gemini/GPT)
      → 如果是文字版 PDF, 用 pdfplumber 还稍微好一点但也不保证
      → 结论: 中文学术论文 PDF → 直接用多模态 LLM 提取, 别浪费生命

十、架构决策记录
================================================================================

  [ADR-001] 预测器是纯规则引擎, 不是 ML 模型
    → 理由: 生物力学规则可解释、零训练、实时性好
    → 副作用: 阈值需要针对具体场景校准
    → 备选方案: 未来加入 Bi-LSTM 学习时序预测 (见下一步优先级4)

  [ADR-002] 预测 + 检测是两条独立管线
    → 预测器 (fall_predictor.py): 事前预警, 基于生物力学规则
    → 检测器 (ml_fall_detector.py): 事后确认, 基于 LightGBM 分类
    → 两者共存互补, 不互相替代

  [ADR-003] 五分类模型已接入 e2e (v4.0)
    → ML5ClassDetector 已正常推理, HUD 上显示 5 类概率条形图
    → 之前交接文档中"暂未接入"是误判, 实际代码中 v4.0 已包含
    → 五分类与二分类并行运行, 互补验证

  [ADR-004] 日志系统独立于检测管线
    → 理由: SQLite WAL 模式 + 批量写入, 不对实时管线产生可感知延迟
    → 默认每 3 帧采样一次 (15 FPS 下约每秒 5 条记录), 每 30 帧或 2 秒批量写入
    → DB 增长估算: ~2MB/天 (5 条/秒 × 200 字节/条 × 8h)
    → 查询和分析走独立连接, 不阻塞写入

  [ADR-005] 告警系统与日志系统完全解耦
    → 告警 (alert_manager): 实时响应, 截图+音频, 内存缓存历史
    → 日志 (activity_logger): 持久化, SQLite, 批量写入
    → 两者各自判断触发条件, 互不依赖
    → 即使日志挂了, 告警仍然工作; 反之亦然
